1. Создай **свою** ветку `work/core-qa-delivery-20261109` от общего SHA, **не** используй ветку второго агента; не push/force-push в чужую ветку и не редактируй его файлы даже «чтобы быстро поправить баг».
2. Для каждой взятой задачи публикуй в PR/issue `[CORE] ID / claimed / branch / expected files / acceptance`. Не отмечай второй поток за себя. Один изменяемый путь имеет **ровно одного хозяина**; при необходимости новых файлов согласуй это через комментарий до коммита.
3. С агентом VISUAL обменивайся только API-контрактами и ссылками на зафиксированный SHA/PR. Пример `VIS-API-01: HUD snapshot(false) [GameApp-owned] → Sprite/UI [Visual-owned]`. Другой агент не имеет права изменять `game/app/game_app.gd`. Аналогично ты не имеешь права изменять `game/ui/game_ui.gd`.
4. Делай маленькие PR, один технический scope на PR, с автотестами; после готового visual PR **только ты** производишь техническую интеграцию обеих веток в новую интеграционную ветку через merge/cherry-pick с проверкой whitelist файлов. Любой конфликт чужого файла возвращай автору: **не редактируй** его вручную.
5. Перед выдачей ZIP один общий SHA проходит Godot 4.7.2 Linux+Windows+docs, настоящие portable Windows offline EXE tests, целостность архива, README/sha; old CI на другой ревизии не засчитывай.
6. В статусе использовать ровно `TODO / CLAIMED / IN_PR / CI_PASS / GUI_PASS / REVIEWED / OWNER_ACCEPTED / BLOCKED / NOT_RUN`. Не утверждать `GUI_PASS`, если доступен только CI/headless, и не объявлять A0-review без отдельного реального отзыва.
7. **Отчёт после каждой подзадачи:** ID → что изменил → перечисление файлов → PR+SHA → точная команда и CI link → PASS/FAIL/NOT_RUN → риск/блокер → следующий owner handoff. Не писать «всё готово» без доказательства.
