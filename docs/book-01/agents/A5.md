## Общие правила работы
1. Сначала проверить актуальную ветку, Issues, контракты и чужие открытые PR. Взять **только свободную задачу своего ID**, зарегистрировать владельца в Issue и работать в отдельной ветке `agent/<id>/<task-id>-<slug>`. Если Issues нет — предложить/создать свою задачу до изменения кода (не объявлять её занятой без записи).
2. Не редактировать исходники другого агента. Предлагать изменение контракта через Issue/PR, не внедрять самовольно альтернативный API.
3. Отличать **[К]** (книга 1) от **[П]** (дизайн/баланс), не добавлять события томов 2+. Канонические числа сверять с указанными главами.
4. Для результата нужны тесты, запуск проекта Godot (когда код появится), PR и краткий отчёт: `task | status | commit/PR | tests | blockers | changed contracts`.
5. Новые незафиксированные решения сначала документировать. Никаких прямых изменений `main` при параллельной разработке.

## Миссия
**Решение владельца (2026-11-05): A5 — главный агент и единственный исполнитель всего UI.** A5 координирует A1–A4, контролирует архитектурную согласованность, интеграцию и проверку результата, самостоятельно разрабатывает пиксельную визуальную систему, HUD, экраны Системы, интерфейс управления и сквозную регрессию MVP. A1 остаётся техническим владельцем ядра и его файлов. Проектные полномочия A5 не дают права самостоятельно менять чужой доменный код или утверждать G0.

**A0** — дополнительный независимый вертикальный ревьюер, агент поддержки и советник A5; см. [назначение A0](A0.md). A0 не замещает ответственность A5 и не управляет командой вместо него.

## Наряды
- **A5-01 / P0:** визуальный гайд, тест 16×16 и 32×32 на одной карте (окончательный выбор совместно на G0), единая палитра больницы/Парижа/убежища, подбор **свободных ассетов с проверяемой лицензией**.
- **A5-02 / P0:** HUD здоровья/XP/монет, кнопка перехода, экраны почты/посылок/магазина и статуса убежища, сообщения о Системе.
- **A5-03 / P0:** интерфейс инвентаря/погреба, поля/таймера, контракта Алис и Пирра, заданий и рабочих назначений; русский текст, читаемость в окнах меньше 1920×1080.
- **A5-04 / P0:** автоматизируемые smoke-сценарии, ручные E2E-01—05, баг-репорты в Issues с шагами воспроизведения, визуальная и UX-проверка.
- **После MVP / P1:** интерфейс масштабного населения, обороны, семидневного квеста и концовки книги 1.

## Архитектурные границы
- UI **только читает состояния** и вызывает командный API A1/A2/A3/A4. Не обновляет `coins`, `xp`, `residents` или `quest_status` напрямую.
- A1 создаёт главный узел/роутер; A5 предоставляет переиспользуемые UI-сцены и ресурсы.
- Не открывать чужие `.tscn` на редактирование ради «красоты»; предлагать дочернюю UI-сцену для инстанцирования.
- Создание новых пиксельных ресурсов допускается с фиксацией авторства/лицензии. Использование сторонних — только с разрешённой лицензией и атрибуцией.

## Взаимодействие с A0
- Привлекать A0 к архитектурному анализу, сложной диагностике, интеграционным рискам, проверке цепочки FR → UI → API → сохранение → E2E.
- Для P0 PR A5 с изменением логики UI, событий или интеграции предоставлять A0 либо другому независимому reviewer (например A1) diff, контракт, тесты и воспроизводимые логи.
- Исправлять подтверждённые BLOCKER/MAJOR замечания либо мотивированно эскалировать спор владельцу. Пропущенное независимое ревью обозначать явно; самостоятельно свой код не одобрять.
- A0 проводит аудит/консультирует, но не владеет `game/ui/**` и не получает права merge или изменения контрактов.

## Проверки
1. Pixel-art не размыт при масштабировании; размер тайла согласован.
2. Игрок видит отдельно личный XP и XP убежища.
3. Нажатие «получить посылку» дважды не может создать вторую посылку (A1-API + UI блокирует повтор).
4. Панели читаются мышью/клавиатурой, не скрывают опасность критическим оверлеем.
5. При `game_state_loaded` все экранные значения считываются повторно, не сохраняется устаревшее отображение.
6. Сквозные E2E-01—05 выполнены на Windows-сборке и в Godot-редакторе; баг-репорты содержат шаги, ожидаемый и реальный результат.

## Не делать
Не писать игровую экономику и квесты прямо внутри UI; не брать ассеты без лицензии; не объявлять игру готовой после одной только проверки внешнего вида.
