## 3. API соответствие: что является нормативным для текущей версии

**Request**: `{action_id,command_type,payload,context:{actor_id,scene_id,expected_resource_revisions:[{key,revision}]}}`. Игровой runtime передаёт координаты и здоровье героя для сохранения и переходов. Для команды, которая записывает контрольную точку, runtime также передаёт `enemy_health` текущего противника. Эти значения заполняют GameApp и SceneRouter.

**Result**: `{ok,code,action_id,state_revision,data,message_key}`. Повтор успешного `action_id` при совпадающем fingerprint даёт `ok=true,code=ALREADY_APPLIED` и прежний receipt без мутации. Действительная операция `SESSION` валидируется по конкретным ресурсам; весь `state_revision` не является глобальным optimistic lock.

**Snapshot**: `CoreSession.get_snapshot()` возвращает `duplicate(true)`; допустим только сериализуемый `CampaignModel`, хранящий `ruleset_version`, `schema_version`, `world_states.layout`, `world_states.locations`, `scene.positions`, `clock_remainder`, `completed_actions`, ресурсы, NPC, crops и квесты.

**События**: `EventBus` публикует уведомления после подтверждённого commit; доставка не является durable ledger. Нельзя вешать получение опыта или создание предмета на callback UI.

**Save/recovery**: `CheckpointStore.write_checkpoint` и `CoreSession.load_checkpoint` с явным backup, pause token и staged runtime scene installation. Ошибка записи не должна приводить к частичному изменению авторитетного state или недостоверному OK.

## Исправление A0/AI-01 / CT-82 — снимок состояния живого зомби (08.11.2026)

**Базовое решение для P0:** при уходе из локации через G, обычную дверь и при сохранении игрок не должен сбрасывать текущую позицию, цель шума или оставшееся время преследования живого зомби. Пока локация не смонтирована, его локальные таймеры не идут. Это соответствует действующему правилу frozen off-scene AI; другие режимы могут быть введены отдельно с миграцией.

**Реализация в PR-кандидате:** опциональный `world_states.enemy_runtime[scene_id]` (совместимый с прежним `schema_version=4`) включает только `position:{x,y}`, `last_noise:{x,y}`, `patrol_index`, `alert_remaining`, `hit_cooldown`. Публикация этих полей происходит **в той же транзакции**, что HP/позиция игрока, в `CampaignCommands.plan`; `scene.transition` получает доверенный снимок текущего Enemy через `SceneRouter`, `session.save` и gameplay-операции — через `GameApp._request`. При возвращении `World.bind` восстанавливает снимок; после необратимой победы удаляется ключ текущей локации, чтобы не воскресить врага. Старые сохранения без поля допустимы и используют начальный AI.

**Контроль целостности:** отклонять неизвестные ключи/нечисловые и бесконечные координаты, отрицательные или избыточные cooldown/alert, незнакомые сцены, запись AI для уже побеждённого врага. При `SAVE_FAILED` обновлённое состояние не публикуется и текущий живой враг не меняется. Старый формат `enemy_health` продолжает загружаться.

**CT-82:** ранить врага; вручную сместить его и поднять aggro; перейти в убежище по G; записать checkpoint; загрузить; выйти физической дверью назад; проверить **равенство `runtime_snapshot()`**, HP, отсутствие второй уникальной награды. Дополнительно: old schema save без `enemy_runtime` проходит `Model.validate`, отрицательный `alert_remaining` отклоняется, побеждённый враг очищает оба snapshot-поля. До зелёного CI и code review статус **FIX_CANDIDATE / NOT_ACCEPTED**.

**Не входит в данный фикс:** обход препятствий (`NavigationAgent2D`, AI-02), полноценные визуальные анимации и ручная Windows-проверка. Не закрывать Issue #63 целиком только по исправлению HP либо без AI acceptance.

## CT-92 / PERF-02 — устранение чтения долговременного журнала при взмахе (08.11.2026)

**Обнаружено в PR #106:** `Player.try_attack` раньше вызывал `GameApp.snapshot()`, который делал `CoreSession._state.duplicate(true)` вместе со всеми `completed_actions` на *каждом* ударе. Измерение PR #106 на 10 000 receipts: медиана взмаха без попадания уменьшалась с 8,090 до 0,066 мс на Linux; эта цифра относится к исходному benchmark на другом SHA, **не к текущему PR**.

**Решение в текущем интеграционном кандидате:** опциональный `CoreSession.get_snapshot(include_receipts: bool = true)` сохраняет обратную совместимость и полностью копирует состояние для команд/сохранения. При `false` на горячем пути удаляет только поле `completed_actions` **до** глубокой копии; `GameApp.snapshot(false)` передаёт это в `Combat.profile`, которому нужны только `player.xp/equipped_weapon_instance_id` и `inventory.items`. Без изменения авторитетного state и без удаления durable receipts. Экипировка и защита от ударов через стены остаются неизменными.

**Автотесты:** `run_core_tests.gd` проверяет, что лёгкая версия не содержит долговременный ledger, полноценный snapshot остался прежним и изменение лёгкой копии не меняет authoritative state. `run_combat_equipment_tests.gd` проверяет, что реальный `Player.try_attack` вообще не запрашивает полную копию. `run_save_profile_tests.gd` на 100/1000/10000 синтетических квитанций сверяет `player` и `inventory`, а на 10 000 печатает длительность 20 полных и 20 лёгких снимков без жёсткого порога, чтобы CI не давал flaky performance FAIL.

**Критерий:** код компилируется; Linux/Windows CI, существующие тесты сохранения, зомби, 51 графическая проверка, 1024 строительства и 28 crash-checks продолжают PASS; производительность фиксируется отдельно без обещания FPS. **30 минут реальной игры и RAM profiling по-прежнему NOT_RUN.**
